# 容器规划调整与验证

日期：2026-10-14。对比基线：提交 `67070e9` 的正式 100 关、300 套方案。图片、48×60 网格、容量上限 40 和基础五槽规则保持一致。

## 最终算法

1. 每次生成一个容器，调用现有模型和最近路径取块逻辑模拟收集，再重新计算各颜色的可达范围。评分兼顾可收集量、近期同色重复和固定种子的随机变化。
2. 前十关不主动引入跨颜色依赖。后续关卡按进度允许最多 1–4 个跨颜色依赖容器；没有合适机会时少生成。已知解法每轮可达收集结束后最多保留一个未完成容器。
3. 同时规划五列。保留容器的解法编号顺序，每列内部按编号递增；当首个颜色的可达数量足够完成两个容器时，将它们安排在两个列头，保留可操作的开局入口。
4. 每个序列评估八种分列候选，每种用四个固定训练种子测试简单选色策略，结合目标通过率、过早失败、开局颜色数和列长差异选择方案。目标通过率随关卡进度从 0.9 降到 0.5，是候选评分参数，不是保证值或玩家通关率。
5. 每关保存三套方案。运行时仅随机选方案、交换整列位置。条目为 `[颜色, 容量, 列号]`，编码成两个 Base85 字符，避免增加微信包体。

实现：`scripts/container-planner.mjs`、`scripts/container-simulation.mjs`、`scripts/generate-container-plans.mjs`。运行时读取：`assets/scripts/domain/game/model.ts`。关卡源模板同步于 `scripts/generate-image2-levels.py`。

## 迭代记录

第一轮加入逐容器规划、同色惩罚、分列筛选及有限跨颜色依赖，消除了连续五个以上同色的方案段落，但随机策略过早失败较多。

第二轮在像素数量允许时为两个可完成的开局容器保留列头。同一组独立种子的 1,500 局随机策略测试中，完成不到 15% 就失败的局数从第一轮 899 降到 826。最终仍比基线 486 高，因此改动不是让随意点击更宽容；可达性和容量判断变得更重要。

构建发现三字符编码使包体达到 4,113.6 KiB，超过微信 4 MiB 限制。改为双字符编码后是 4,086.0 KiB，300 套方案的解码哈希完全不变。

## 实际路径与组件流程

- 最近路径策略抽查第 1、3、4、10、20、60、100 关，覆盖各自三套方案，新旧共 126 局。简单选色策略新旧均为 15 / 21；容量策略从 16 / 21 提升到 20 / 21。样本较小，不能据此推算所有关卡；结果支持更仔细的容量判断在新方案中有实际收益。数据：`art/container-evaluation-nearest.json`。
- 同样七个关卡的三套新方案，共 21 次真实 `PixelGarden.update` 重放，包含预测预占、派工、取块、飞行及送达，均通关。选择策略是等待当前可达工作完成后选择下一个解法容器。渲染使用模拟器，不涉及浏览器、真机 FPS 或触摸体验。
- 全部 300 套方案在源模型中按实际最近路径重放，检查列头合法性、五槽可解性、逐色容量守恒、方案哈希、整列交换不破坏解法。
- 微信构建产物也对全部 300 套方案执行相同的可解性检查。

## 复现与发布

```sh
npm run generate:containers
npm run evaluate:containers
npm run evaluate:containers -- --nearest --levels 1,3,4,10,20,60,100 --trials 1 --output art/container-evaluation-nearest.json
CONTAINER_LEVELS=1,3,4,10,20,60,100 CONTAINER_VARIANTS=0,1,2 npm run check:containers
npm run check
npm run build:wechat
```

`evaluate:containers` 默认只评估当前方案；可用 `--baseline` 传入由旧版本导出的 `Level[]` JSON，条目同样使用 `[颜色, 容量, 列号]`，进行对照。默认命令会覆盖评估报告，可通过 `--output` 指定其他路径保存新结果。

容器数量变化已同步生成 `cloudfunctions/game/catalog.json`。上线应配套发布客户端及云端目录，否则旧云端的通关步数校验可能拒绝新方案成绩。
